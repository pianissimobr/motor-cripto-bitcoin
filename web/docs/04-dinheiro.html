Parte 2 · O método

Dinheiro

Reais são centavos inteiros. USDC é uma string de unidades mínimas. A taxa fica congelada no link. A tolerância diz o que ainda conta como valor cheio.

ObjetivoCalcular o esperado de uma cobrança e ler valor_recebido_base_units sem usar número decimal solto.

O problema

R$ 150,00 escrito como 150.00 num JSON convida erro de arredondamento. USDC tem 6 casas. 0.18 vezes 150 não é uma conta que se faça com ponto flutuante quando o resultado vai para a rede.

O método

A loja envia amount_cents: 15000. O perfil guarda a taxa 180000, que significa 180000 unidades mínimas de USDC por R$ 1,00. Como o USDC tem 6 decimais, 180000 unidades são 0,18 USDC.

15000 centavos = 150 reais
150 × 180000 = 27000000 unidades mínimas
27000000 / 10^6 = 27 USDC

O link grava expected_base_units: "27000000" na criação. Se alguém atualizar a taxa do perfil amanhã, esta cobrança continua comparando com 27 USDC. A comparação usa a taxa do nascimento, não a taxa viva.

A tolerância padrão é 1% (PAYMENT_TOLERANCE_PCT). Dentro dela, o recebido pode ir a pago. Fora dela, para menos, fica parcial. Para mais, o extra também é registrado e varrido: o motor não devolve o que sobrou para a Ramp.

O valor que realmente chegou aparece em valor_recebido_base_units, sempre string. Some com inteiro grande, não com Number de JavaScript se o valor puder passar de 2^53.

amount_cents aceita de 1 a 100000000 (um milhão de reais). A taxa, quando enviada, é string de dígitos ou inteiro não negativo.

O que recusamos

  • Corpo com "amount_cents": 150.00 ou string. O campo é inteiro.
  • Usar a cotação do dia lida na hora do webhook. A referência é a taxa gravada.
  • Recusar dinheiro que chegou a mais ou a menos. A menos, fora da tolerância, muda o estado. O token se move mesmo assim.

Como conferir

Como conferirCrie o link de 15000 centavos no perfil de taxa 180000 e 6 decimais. A resposta traz expected_base_units igual a "27000000". Se vier outro número, a taxa do perfil não é a do exemplo.
