Parte 1 · O objetivo

O objetivo

A loja quer receber Bitcoin. Quem paga escolhe Lightning ou a rede principal. O motor cria a cobrança, percebe o pagamento e move o valor on-chain para a carteira fria.

ObjetivoExplicar, sem abrir o código, o que o motor faz e o que ele se recusa a fazer.

O problema

Imagine um pedido de 10.000 satoshis. A loja precisa de um QR que sirva para os dois trilhos, de um aviso quando o pagamento cair, e de um prazo para não deixar o pedido aberto para sempre. Sem isso, alguém teria de olhar a carteira e a invoice à mão.

O destino on-chain não é uma carteira escolhida pela loja em cada pedido. Todas as cobranças varrem para a carteira fria configurada no operador, COLD_WALLET_ADDRESS. O Lightning cai na wallet do LNbits que o operador conectou. O motor separa os pedidos por cliente da API; o dinheiro físico dos dois trilhos fica sob a custódia dessa operação.

O método

  1. O operador cria o cliente da API e anota, uma única vez, a chave, o segredo de pedido e o segredo de webhook.
  2. O sistema da loja pede uma cobrança com external_id e amount_sats.
  3. O motor reserva um índice, deriva um endereço Bitcoin exclusivo e pede uma invoice ao LNbits.
  4. A resposta traz a invoice, o endereço, a URI BIP21 e o SVG do QR. A loja mostra isso a quem paga. Não há página hospedada pelo motor.
  5. O worker confirma o Lightning no LNbits e lê os UTXOs no Esplora. Com as confirmações exigidas, avisa a loja.
  6. O valor on-chain confirmado é assinado no worker e enviado à carteira fria. O Lightning permanece no LNbits.

O contrato

O objetivo vira duas superfícies HTTP no mesmo processo, na porta local 4580 ou na PUBLIC_BASE_URL:

  • /admin/api/* para quem opera, com o ADMIN_TOKEN.
  • /v1/* para o sistema da loja, com API key e assinatura de cada pedido.

/health e /ready não pedem segredo. O webhook de entrada do LNbits é POST /webhooks/lnbits. O valor viaja como string de satoshis. A invoice e o endereço saem no JSON da cobrança, porque a loja é quem exibe o QR.

O que recusamos

  • Receber reais, cartão, Pix ou stablecoin.
  • Aceitar um endereço de depósito enviado pela loja.
  • Reutilizar um endereço Bitcoin entre cobranças.
  • Tratar um e-mail, um print ou o corpo cru do webhook do LNbits como pagamento.
  • Confirmar o on-chain antes das confirmações exigidas.
  • Colocar a chave privada ou a seed na API. A API só tem o xpub.

Como conferir

Como conferirAbra /health. A resposta traz ok: true, o nome btc-payments e ts em UTC, sem token. Se isso responde, a API está no ar. O pagamento em si só existe depois do worker, do LNbits e do Esplora. /ready diz se esses três, o xpub e a carteira fria estão utilizáveis.
