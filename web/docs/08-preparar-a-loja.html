Parte 3 · O contrato

Preparar a loja

Antes da primeira cobrança existem três cadastros: o cliente da API, a carteira de destino e o perfil Ramp. Dois deles são trabalho do operador. O terceiro a loja só lê.

ObjetivoDeixar um cliente apto a criar link: segredos anotados, carteira allowlisted na rede certa, perfil cujo contrato não vai mudar.

O problema

Se a carteira de destino fosse um campo livre na cobrança, uma chave vazada escolheria para onde o dinheiro vai. Se o contrato do perfil pudesse ser trocado depois, links já abertos deixariam de ser observados. A preparação trava essas duas decisões.

O método

  1. O operador cria o cliente com nome e webhook_url. A resposta de 201 traz api_key, request_secret e webhook_secret fora do objeto data. É a única vez. A listagem posterior mostra só api_key_prefix.
  2. O operador cadastra a carteira: rótulo, chain e endereço 0x de 40 hex. A chain precisa existir no motor.
  3. O sistema da loja, já com a assinatura, lê GET /v1/ramp-profiles e GET /v1/wallets. Guarda os dois ids. Na cobrança eles viajam juntos, e a chain da carteira tem de ser a do perfil.

Chains aceitas: polygon, amoy, arbitrum, base, ethereum. Nome desconhecido responde 400 antes de existir carteira ou perfil.

A URL de webhook, em produção, só aceita https. Em qualquer ambiente o motor recusa localhost, endereço de loopback, rede link-local, o endereço de metadata 169.254.169.254 e um nome que resolva para IP privado. A checagem é na gravação, não a cada tentativa de entrega.

O contrato

Criar cliente

POST /admin/api/clientes
Authorization: Bearer $ADMIN_TOKEN
Content-Type: application/json

{"nome":"Loja Exemplo","webhook_url":"https://loja.example/webhooks/motor"}

Resposta 201: data com id, nome, api_key_prefix, webhook_url, status: "ativo", criado_em, e ao lado api_key, request_secret, webhook_secret.

PATCH /admin/api/clientes/:id aceita nome, webhook_url e status (ativo ou inativo). Cliente inativo não autentica. Pelo menos um campo.

POST .../rotate-key troca a API key e o request secret na hora. POST .../rotate-webhook-secret troca só o segredo dos webhooks. De novo, o segredo novo aparece uma vez.

Cadastrar carteira

POST /admin/api/clientes/:id/wallets

{"label":"Carteira principal","chain":"polygon","address":"0x1111111111111111111111111111111111111111"}

O endereço volta normalizado. Carteira repetida para o mesmo cliente é 400.

Perfil Ramp

A criação, pelo admin, fixa label, chain, asset, token_contract, decimals, fiat_currency, base_url, param_style (legacy ou unified), host_app_name, e os opcionais host_logo_url, host_api_key, ramp_asset_key, taxa_token_por_fiat_base_units.

O PATCH só aceita o que não muda o ativo observado: label, fiat_currency, base_url, param_style, host_app_name, host_logo_url, host_api_key, ramp_asset_key, taxa_token_por_fiat_base_units. Enviar token_contract ou chain responde 400. Para outro contrato, crie outro perfil. Links já abertos continuam sendo lidos no contrato em que nasceram.

host_api_key não volta em nenhuma leitura.

O que recusamos

  • Webhook http:// quando o processo está em produção.
  • Webhook apontando para a própria máquina, para a rede interna ou para o endereço de metadata.
  • Chain fora da lista.
  • Endereço que não seja 0x mais 40 hexadecimais.
  • Mudar contrato, ativo, rede ou decimais de um perfil já criado.

Como conferir

Como conferirGET /v1/wallets assinado devolve a carteira com o id que vai em wallet_id. GET /v1/ramp-profiles devolve o perfil sem host_api_key. Guarde os dois ids antes de criar o link.
