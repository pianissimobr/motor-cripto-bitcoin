Um dia inteiro

A sequência que a pessoa implementa olhando. Os corpos são o exemplo-mestre: R$ 150,00, USDC na Polygon, 27 USDC esperados. Troque os segredos pelos seus. Não use estes uuids em produção; eles são didáticos.

ObjetivoSair com um link aguardando, uma página aberta e um verificador de webhook pronto para quando o worker vir o pagamento.

O problema

Os capítulos anteriores separam as ideias. Na integração elas acontecem numa tarde só, e o erro mais comum é assinar um JSON diferente do que o HTTP envia, ou guardar a API key e esquecer o request_secret.

O método

Base local: http://localhost:4578. O worker precisa estar rodando para o passo do pagamento. A carteira de POL precisa ter saldo para o passo da varredura. Estes dois não são chamadas da loja.

1. Cliente

curl -sS -X POST http://localhost:4578/admin/api/clientes \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"nome":"Loja Exemplo","webhook_url":"https://loja.example/webhooks/motor"}'

Guarde api_key, request_secret e webhook_secret agora. Anote o data.id.

2. Carteira

curl -sS -X POST http://localhost:4578/admin/api/clientes/CLIENTE_ID/wallets \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"label":"Carteira principal","chain":"polygon","address":"0x1111111111111111111111111111111111111111"}'

Anote data.id como wallet_id.

3. Perfil

Assine GET /v1/ramp-profiles e escolha o perfil Polygon USDC. A taxa do seed de exemplo é "180000". Anote o id.

4. Link

Corpo, uma string só:

{"external_id":"pedido-150","amount_cents":15000,"ramp_profile_id":"PERFIL_ID","wallet_id":"WALLET_ID"}

Assine POST + /v1/links + timestamp + nonce + SHA-256 desse texto. Envie com Idempotency-Key: pedido-150. Espere 201, reused: false, expected_base_units "27000000" e uma page_url.

5. Página

Abra a page_url. O valor é R$ 150,00. O status público, sem autenticação, repete aguardando.

6. Quando o USDC chegar

O webhook de pago traz valor_recebido_base_units "27000000" se o valor veio cheio. O header x-webhook-signature tem a forma t=<unix>,v1=<hex>. O hex é HMAC-SHA256 do webhook_secret sobre timestamp.corpo, usando o corpo cru. Responda 204 rápido. Grave o event_id. Não entregue o pedido só com este aviso se a sua regra de negócio exige o token já na carteira: espere o evento cujo data.status é movido.

O contrato

O verificador mínimo, em Node, para um corpo já lido como string:

import { createHmac, timingSafeEqual } from 'node:crypto';

function ok(secret, signatureHeader, rawBody) {
  const partes = Object.fromEntries(signatureHeader.split(',').map((p) => p.split('=')));
  const esperado = createHmac('sha256', secret).update(`${partes.t}.${rawBody}`).digest('hex');
  const recebido = partes.v1 ?? '';
  if (esperado.length !== recebido.length) return false;
  return timingSafeEqual(Buffer.from(esperado), Buffer.from(recebido));
}

Isto confere a assinatura do header x-webhook-signature. A janela do timestamp t fica a cargo da loja. O processamento do pedido fica depois do 204, numa fila sua.

O que recusamos

  • Pular a carteira e mandar um endereço solto no POST /v1/links. Esse campo não existe.
  • Reenviar a criação com outro amount_cents e a mesma Idempotency-Key. É 409.
  • Considerar o dia terminado no pago se você prometeu à operação que o USDC já está na carteira allowlisted.

Como conferir

Como conferirA resposta do link tem page_url e não tem ramp_url. A página mostra o botão. GET /v1/links/ID devolve o mesmo id. Quando o worker estiver no ar e o pagamento confirmar, o primeiro webhook e o GET concordam no status.
