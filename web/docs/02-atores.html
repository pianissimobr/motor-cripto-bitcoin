O que você configura

Tudo isto vai em services/btc-payments/.env. O serviço não escolhe esses valores. O arquivo na raiz do repositório é de outro processo e esta API não o lê.

VariávelO que é
ADMIN_TOKENSenha sua para /admin/api/. No ambiente local de exemplo, dev-admin-token-change-me.
DATA_ENCRYPTION_KEYCifra os segredos das lojas no banco. Trocar a chave deixa o que já foi gravado ilegível.
DATABASE_URLO Postgres deste serviço.
BTC_NETWORKregtest no exemplo. Em rede real, bitcoin.
BTC_XPUBChave pública da conta m/84'/0'/0'. A API deriva os endereços com ela. O xprv não entra neste arquivo.
LNBITS_URL e LNBITS_API_KEYA wallet que emite as invoices. A key é a Invoice Key dessa wallet.
LNBITS_WEBHOOK_TOKENSegredo que o LNbits devolve quando alguém paga.
ESPLORA_URLDe onde o worker lê UTXO, confirmação e taxa.
COLD_WALLET_ADDRESSEndereço da mesma rede, para onde o on-chain é varrido. A chave privada fica com você.
SIGNER_PASSPHRASEAbre o keystore do worker, onde está o xprv que assina o sweep.

Depois que isso existe, o serviço cria sozinho a API key de cada loja, o endereço de cada cobrança, a invoice e o QR. npm run wallet:init mostra o mnemonic uma vez, se o signer for local. Esse mnemonic é o que você guarda.

O xpub do .env de exemplo vem de um mnemonic público, só para regtest. Em mainnet você coloca o seu xpub e um COLD_WALLET_ADDRESS seu.

Três papéis

  • Você opera com o ADMIN_TOKEN. Cria lojas, olha o status, reenvia webhook e pede retry de sweep.
  • A loja chama /v1/* com a API key e o HMAC. Ela escolhe o external_id e o valor. Não escolhe o endereço.
  • Quem paga vê o QR na tela da loja e não chama a API.
CuidadoVárias lojas podem existir. O sweep de todas vai para a mesma carteira fria, e o Lightning de todas cai na mesma wallet do LNbits.
